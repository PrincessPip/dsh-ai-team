# 任务书 · REVIEW-BRIEF（示例）

> 这是 `examples/minimal/` 的样例任务书，用来演示**一份能被独立复核的任务书长什么样**。
> 模板见 `templates/REVIEW-BRIEF.md`；本文件演示的是「填完之后」的形态。
> 目标工作区：`/path/to/workspace`（一个只有三个文件的极小仓库，见 `README.md` 的重现步骤）。

---

## 一、头部

| 字段 | 值 |
|---|---|
| 交付单元 | `SLUG-DEMO-01` |
| 送审轮次 | `round 1` |
| **谁发起的送审** | `Lead`（**不是**实现者本人） |
| 验收范围 | `src/slug.js` 的最终内容与行为；`README.md` 与实现是否一致 |
| 明确不在范围 | 编辑过程的时间顺序；代码风格；未来可能加的配置项 |
| 工作区 | `/path/to/workspace` |
| 时间 / 预算上限 | 15 分钟 / 1 次后端调用 |

## 二、要验收什么

| # | 验收标准 | 类型 | 最低强度 |
|---|---|---|---|
| C1 | `src/slug.js` 导出一个函数 `slugify(input: string): string`，把任意大小写与空白的字符串转成小写、以单个 `-` 连接的 slug；空输入返回空字符串 | `executable` | `E3` |
| C2 | 仓库里有针对 `slugify` 的自动化测试，且能被一条命令跑起来、全部通过 | `executable` | `E3` |
| C3 | `README.md` 里给出的示例调用与 `src/slug.js` 的实际行为一致 | `fact-consistent` | `E2` |

## 三、证据要求

- 每条 `pass` 必须给 `file:line` + 锚串，或命令 + 输出摘要（**由命令直接落盘**）。
- 强度自报 `E0`–`E3`；`E3` 需要**至少一个反证**（造一个本该失败的情形，确认它真的失败）。
- `C1` / `C2` 属 `executable`，**证据不够 `E3` 就判 `fail`**，不许「差不多算交叉验证」。
- `C3` 属 `fact-consistent`，可以按**位置独立性**折算：同一事实在 `README.md` 与实现里一致 = `E2`。

**本单元特别要求**：

- [ ] `C2` 的反证请具体：把测试文件里的一条断言故意改错，确认测试**变红**；再改回来，确认**变绿**。
      （只有「跑绿了」= `E1`；「改错会红」才证明这套测试真的在判。）
- [ ] `C3` 请真的**跑一次** README 里的示例调用，不要只读代码推断。

## 四、你可能会踩到的两个坑（本单元的现场信息）

1. **实现与 README 可能一致地错。** 两个位置写着同一个错误结论 = 位置独立但事实错 —— 这不算 `E2`。
   位置独立性折算的前提是「同一个事实」，且事实得先是真的。
2. **测试文件存在 ≠ 测试在跑。** 检查它是否真的被测试命令收集到（看输出里的用例数），
   而不是只看文件在不在。

**工人自述的位置**：`DELIVERY.md`（本样例未随附，视为「只有口头声明、没有交付包」——
这正好演示了本轮为什么会被判 `rework`）。

⚠️ **先自己按 §二 在仓库里找证据，再读工人自述。** 顺序反了，就只是复述。

## 五、输出格式

按 `templates/REVIEW-BRIEF.md` §五 的 JSON 形状输出。
`rework_brief` 必须写明返工类别：`事实存疑` / `判据可能没在判` / `修完一个真 bug` / `声明缺失` / `引用格式` / `材料形式`。
