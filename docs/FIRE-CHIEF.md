## 一、它是什么

**一个「能写、能跑、能自己落盘证据」的干活位**，走**订阅额度**，不是验收官。

命令形态（由 `scripts/fire-chief.py` 统一发起，**不手敲**）：

| 引擎 | 命令 | 额度窗口 |
|---|---|---|
| **codex（默认，v3.0 起）** | `codex exec --json -m gpt-6-astra -c model_reasoning_effort=high --approve-for-me -C <工程根> <指路 prompt>` | ChatGPT **7 天**周窗口 |
| claude（备用） | `claude -p --model opus --allowedTools Read,Grep,Glob,Bash,Write,Edit <prompt>` | Claude **5h** 窗口 |

**为什么默认换成 GPT-6 Astra（伙伴 2026-11-11 拍板）**：

1. **两条窗口独立** —— 「一个 5h 窗口装不下救火 + 两轮验收」已经撞过两次（`tasks/FIRE-CHIEF-2026-11-10/HANDOVER.md` §一）；
2. **跨模型** —— 验收官仍是 Opus，于是 §七 末尾那条「同模型同盲区」自动降级；
3. 它本身更强。

⚠️ **订阅里能拿到的最好档就是 `gpt-6-astra`**：`gpt-6-astra-pro` 订阅通道返回
HTTP 400 `model_not_found`（原文 `not supported when using Codex with a ChatGPT account`），只在按量计费有。
通则「我指的 GPT 模型，优先选择订阅服务里的模型」= 先看订阅，订阅里没有才谈按量，而按量必须先问。

## 二、为什么需要它（拿刚发生的事做论据）

C7 那条判据从第 1 轮卡到第 5 轮。回头看，**功能面第 1 轮就全绿**，
后面三轮卡的全是「证据怎么做实」：我把探针删了、stdout 没落盘 → `escalate`；
把同一次 stdout 的两行当两个维度 → 自查打回；
反证切在「文件存续」而不是「白名单变量」上 → `rework`。

真正救我的是**一个有 shell 的 opus 当场跑、当场把 transcript 写下来**（三次实验，59s/37s/32s）。

→ **它的卖点不是「更会写代码」，而是「干活的时候顺手把可核证据产出来」。**
如果第 3 轮就派它接手「跑实验 + 落盘 + 出证据」，大概率第 4 轮就过了。

## 三、和现有角色的边界（最容易搞混的地方）

| 角色 | 通道 | 能写吗 | 能自审吗 | 干什么 |
|---|---|---|---|---|
| 工人（我） | deepseek | ✅ | ❌ | 实现、自测、写交付包 |
| 验收官 | `subagent_claude_code` / `claude -p`（只读） | ❌ | —— | 独立复核 |
| 总经理（`scripts/manager.py`） | `claude -p --model opus --json-schema` | 只写 `GRAPH.json` | ❌ | 出图，**不干活** |
| **救火队长** | **`codex exec -m gpt-6-astra`（默认）** / `claude -p --model opus`（备用） | ✅ **白名单内** | ❌ **不能自审** | 卡死后接手 + 当场出证据 |

- **和总经理的区别**：总经理只出图；救火队长直接改代码。
- **和验收官的区别**：权限模型**相反** —— 验收官 `dontAsk` 只读，救火队长要写。
  **所以它必须走另一个通道**，而且不能自己验自己。
- ⚠️ 顺带**两条**硬事实（2026-11-07 第 2 轮验收官 N1 指出：原来只写了第一条，会误导）：
  ① `subagent` 工具在这台机器上**只有 `openrouter` 一条路由**（按量计费）；
  ② `subagent_claude_code` **走原生 `~/.claude`、也是订阅额度**，但它的 `dontAsk` **天然只读** +
  文件访问**锁在子级工作目录内** —— **它写不了**。
  所以「想走订阅就必须用 CLI」这个**结论**对，**但理由不是「只有 openrouter」**，
  而是「另一条订阅通道没有写权限」。

## 四、触发条件（两路 + 点名 · 2026-11-07 起**不需要每次点头**，2026-11-11 收紧）

| 档 | 条件 | 谁触发 |
|---|---|---|
| **B · 消耗型**（v3.0 收紧） | 同一交付单元**累计 2 次独立裁决非 pass** → **当场派**，不等第 3 轮 | 我判定 → **直接派** |
| **A · 能力型**（该派） | 同一个**功能/行为**类 blocking 修了 ≥2 次还错；或我明确说不出根因 | 我判定 → **直接派** |
| **点名** | 伙伴直接说「派救火队长」 | 伙伴 |
| **不该派**（v3.0 降级为建议） | 纯文档 / 分类 / 跨文件同步问题 —— 只在自动 A 与点名时参考 | 命中自动 B 时**照样派** |

**「独立裁决」怎么算**：送审任一轮判 `rework` / `escalate` 各算一次；抽检打回也算一次；
同一轮里两判**算两次**。累计到 2 就触发 B。

⚠️ **与 `escalate` 抢方向盘时谁优先**（2026-11-11 第 1 轮验收官 B3 指出原稿没写这条）：
`REVIEW-CONTRACT.md` §六 规定「第 2 轮仍 `rework` → 自动升级为 `escalate`」，意思正是「问题可能不在执行层」。
所以按 `escalate` 的**六条红线分组**处置：

| 红线 | 处置 |
|---|---|
| **1–3**（要人取舍 / 涉钱与权限 / 需求有歧义） | **不自动派**，先交伙伴 —— 换谁干都答不了「我们要什么」 |
| **4–6**（判断冲突 / 验不了 / 信心不足） | **照样自动派** —— 这三条正是该换手的信号 |

判据细节在 `TRIGGER-POLICY.md` §二·五·一·二，这里不复制。

**救火轮上限 2 次**（v3.0 新增）：第 2 次救火仍被验收官判非 pass → **停止自动派，找伙伴**。
理由：那时候分歧在口径不在能力，再派只是把同一个分歧再烧一遍。

⚠️ **「A/B 都要伙伴点头」已废（2026-11-07 伙伴拍板）**。代价是自动两路花的是订阅额度、且带写权限，
所以**每次触发都必须在账本留一条可审计的触发事实**（第几轮、什么 blocking、为什么够格）。
成本口径随引擎变：codex 走**周窗口**（7 天，只报 `usedPercent`），claude 走 **5h 窗口**（一次 opus ≈ 3%）。

## 五、权限与证据（直接照 C7 三次实验的现成做法）

1. **事故单** `INC-<date>-<n>.md`：写死「可写面白名单」+ 任务 + 失败史（前几次为什么没过）。
2. **跑**：上面那条命令，`prompt` 只给事故单路径（**指路式**，长中文 prompt 走 CLI 会损坏）。
3. **取证**（核心）：落进 `runs/fire/<id>/`，**不是我事后手抄**。⚠️ 2026-11-11（`DOC-SYNC-2026-11-11`）起**分工改了**：
   `TRANSCRIPT.log` / `CHANGES.md` / `SNAPSHOT.txt` 三件由 `scripts/fire-chief.py` 渲染
   （命令流水只有执行进程看得见，模型拿不到自己的完整命令记录），**救火队长只写 `VERIFY.md`**。
4. **两道核（2026-11-07 起）**：① 我做**交付包体检**（快照 diff / 四件齐不齐 / 回归真跑过）—— **不出合格证**；
   ② **标准验收官**（Opus，独立对话，**带 shell**）逐条核完成条件、自己跑命令复现，**唯一出裁决**。细则见 `TRIGGER-POLICY.md` §二·五·三。
5. **账本**：记 1 行，档位标「救火」+ 事故单路径 + 独立核的结论。

## 七、四个点的拍板结果（2026-11-07 伙伴逐点过）

| # | 点 | 结论 | 落在哪 |
|---|---|---|---|
| 1 | 谁审它的活 | **不自建验收轮 ≠ 不验收**。走**标准验收官（Opus 5.5，独立对话，带 shell）**出最终裁决；我的机械核降级为「交付包体检」，**不出合格证** | `TRIGGER-POLICY.md` §二·五·三 |
| 2 | 写面怎么划 | **读宽、写窄**。写 = 文件级白名单（目录级只留新建产物目录）；读 = **工程仓全域只读不设限**，用**上下文交接清单**补齐「我知晓什么」。意料之外的发现**只报不改** | §二·五·二 + `INC-TEMPLATE.md` §二·五 / §4.4 |
| 3 | 额度（原「闸」已撤） | **只记录，不设闸**（耗时 + 是否撞顶）。理由：`claude` CLI 没有可靠用量查询接口，拿测不准的数做闸等于装假表 | §二·五·四 |
| 4 | 能不能碰 `scripts/` | 能改**干活的**脚本；**判据类四个文件点名禁改** + `git` 写操作全禁。**送审是事后，禁改是事前** | §二·五·五 |

**另加一条原方案没有的**：触发改成**两路**——自动（A/B 阈值，**不再需要每次点头**）+ 伙伴点名。
代价是每次触发必须在账本留一条可审计的「触发事实」。见 §二·五·一。

**「同模型同盲区」这条（2026-11-11 按事实改写）**：
2026-11-07 写下的是「救火队长与验收官**是同一个模型**，只能缓解不能消除」。
v3.0 换成 GPT-6 Astra 之后，**主力路径上这条弱点不再成立**：执行体 GPT、裁决方 Opus，是两个模型。
所以它从「结构性弱点」降级为「备用通道的局限」：

| 路径 | 是否同模型 | 要怎么办 |
|---|---|---|
| **默认（codex / gpt-6-astra）** | 否 | 仍要保留三条纪律：上下文完全独立 · 契约反顺从 · **必须自己复现**。这次是纪律，不是补丁 |
| `--engine claude`（Opus 备用） | **是** | 三条重新当成「唯一缓解」，别当已解决 |

**但换模型没解决的那一半要写清楚**：两个模型都可能**被同一份中文契约骗过去** ——
契约里写了「这样做算数」，两个模型都会照办。所以「证据怎么做实」这件事，
最终仍要靠 `REVIEW-CONTRACT.md` 的判据本身够硬，而不是靠换个更聪明的脑子。

## 八、还没想清楚的地方（如实 · 2026-11-11 按换模型后的形态重写）

- **GPT 没读过我们这堆中文契约，比 Opus 那次更没底。** C7 卡的很多是「我们的规矩」
  （D 分类、账本口径、证据写法），不是通用工程能力。第二次实战（Opus）已经证明：
  **事故单写得够不够自含，直接决定它一次过还是返工**。换成 GPT 后这一条的权重只会更高，
  所以 `INC-TEMPLATE.md` §二·五 与 §六 两节从「建议填」变成**事实上的成败手**。
- **它对 Windows 中文环境不熟**（2026-11-11 实测里它自己选了 `[System.IO.File]::ReadAllLines(…, UTF8)`，
  算是运气好）。模板已把读法写死，但「它会不会照做」没用真救火验证过 —— **这是本版最大的未知**。
- **写权限仍是第一个破口**。白名单是**提示词约束不是硬锁**（它能写任何地方），
  兜底只有「事后全树 sha256 对账」。`fire-chief.py` 把这个兜底自动化了，但**仍是事后**。
- **它写的代码谁来维护**：风格与 `runner.py` / `manager.py` 不一致的话，下一个人（我）要付税。
- **成本口径换了**：codex 走 7 天周窗口，`usedPercent` 四舍五入经常是 0 —— 看不见用量，
  只能看「有没有撞顶」。这比 claude 的 5h 窗口**更不透明**，别假装能算账。

## 九、和 P3（agent-team 按领域招人）的关系

救火队长其实是 C 档「按领域招人」的一个特例：**唯一一个被授权写代码的外部模型位**。
P3 真开的时候它应该是 roster 里的固定一员（`gpt-fire-chief`，备用 `claude-fire-chief`），
而不是外挂脚本 —— 现在 `scripts/fire-chief.py` 就是那个「外挂」的过渡形态。
